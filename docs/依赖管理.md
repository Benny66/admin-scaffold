# 依赖管理

本项目的依赖管理采用「**显式登记制**」：新增依赖不是禁止，而是**必须登记 + 写理由**，由 guard 测试强制执行。

## 为什么要登记制

早期用「硬禁单」（`禁止引入 excelize / echarts / qrcode`）管理依赖，存在两个问题：

1. **自相矛盾**：被禁的 `excelize`（Excel）、`echarts`（图表）、`qrcode`（二维码）都是可跨项目复用的通用库，恰恰满足「通用依赖」的判据，不该被禁。
2. **无执行力**：禁单是散文，没有 guard 测试兜底，AI 违反时 `make test` 依然是绿的。

登记制把「约束」变成「可执行的检查」：依赖是否合法，由「是否已登记」判定，而非「是否在某个禁单里」。

## 怎么加依赖

以「为资产项目引入 Excel 导入导出」为例：

1. 执行 `go get github.com/xuri/excelize/v2`（或 `npm install ...`）。
2. 在根 [`deps.yaml`](deps.yaml) 对应端下追加一条：

   ```yaml
   backend:
     - package: github.com/xuri/excelize/v2
       reason: 资产/员工批量导入导出
   ```

3. 跑 `make test` 确认通过。

就这么简单。漏了第 2 步，guard 测试会红，提示「依赖 X 未登记」。

## 登记范围

只登记**直接依赖**，不登记传递依赖与工具链：

| 端 | 登记源 | 跳过 |
|---|---|---|
| 后端 | `go.mod` 主 `require (...)` 块 | `// indirect` 间接依赖 |
| 前端 | `frontend/package.json` 的 `dependencies` | `devDependencies` |
| 移动端 | `mobile/package.json` 的 `dependencies` | `devDependencies` |

## guard 如何校验

`backend/internal/guard/deps_test.go` 的 `Test_UnregisteredDependency` 做双向断言：

- **正向**：依赖清单里每个直接依赖都出现在 `deps.yaml`，否则失败（「未登记」）。
- **反向**：`deps.yaml` 每个登记项都真实存在于清单，否则失败（「僵尸条目 / typo」）。

## 判据提示（非硬禁）

登记理由的写法建议：优先选择**可跨项目复用的通用依赖**，把业务专属逻辑挡在基座之外。这是「好品味」的提示，不是「禁止」的依据——具体项目需要什么，登记即可。
