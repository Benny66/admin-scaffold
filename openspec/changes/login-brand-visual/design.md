# Design: login-brand-visual

## Context

登录页是系统的第一屏，也是品牌的第一印象。现状（`frontend/src/views/Login.vue`）：全屏渐变 `linear-gradient(135deg, #1f6feb, #0d3b8c)`，中间一个 380px 白卡片，卡片里是系统名 + 硬编码副标题 + 两个输入框 + 一个按钮 + 一句默认账号提示（L76-111）。移动端（`mobile/src/views/Login.vue`）是另一套：渐变背景 + 居中 logo/标题 + Vant 表单。

两端既没有共享品牌层，也没有主题 token——`#001529`、`#1f6feb`、`#0d3b8c` 散落在各组件的 scoped style 里。

**已经通了的管道**：`/static` 静态服务（`backend/router/router.go:13`）在桌面端 dev（5173 proxy）、移动端 dev（5174 proxy）、生产单二进制三个场景下都已打通，且 `staticURL()` 返回绝对路径 `/static/<file>`，所以移动端挂在 `/m/` 前缀下也不会解析错。这意味着「可配置背景图」不需要新建任何管道，只是顺着已有管道多传两个文件名。

**没通的管道**：`subtitle` 后端返回但前端不收（详见 `brand-config-guard`）；footer 只在 Layout 内渲染，登录页在 Layout 外。

## Goals / Non-Goals

**Goals:**

1. 桌面端登录页改为左图右表单分栏，左栏背景图可通过 `config.yaml` 配置。
2. 移动端登录页支持可配置背景图，并补上 footer。
3. 两端共享 footer 组件与品牌块渲染，消除重复。
4. 背景图未配置或加载失败时，回退到渐变，保证零配置也好看。
5. 顺带清掉登录页与移动端首页的生产环境隐患（默认账号提示、favicon 404、密码管理器失效、猫图外链）。

**Non-Goals:**

- 不做全局主题 token 体系 / 暗色模式（见 Open Questions）。
- 不做验证码、记住密码、失败锁定（后端 `services.Login` 无对应能力，见 Open Questions）。
- 不改 `GetSystemInfo` 既有字段的语义，只新增两个。
- 不引入动画/图表库，所有效果用原生 CSS。

## Decisions

### D1：始终分栏，左栏背景是「图片 or 渐变」的可换层

不采用「有图才分栏、无图就回到居中卡片」的条件布局，而是**始终分栏**；左栏的背景是一个可替换层：配了 `login_bg` 就是图片 + scrim，没配就是渐变（**不叠 scrim**）。

**Why：** 决定性理由是「无背景图」并非边缘情况，而是**基座的默认路径**——`backend/static/` 现在只有 `logo.png`，没有任何背景图，任何 clone 本基座的人第一眼看到的都是未配置状态。若采用条件布局，绝大多数使用者永远不会配置背景图，也就永远看不到新设计，等于把这次改版藏在一条没人走的路径后面。而「渐变 + 品牌块」本身已优于现状的裸卡片，零配置用户同样是收益方。

**最坏情况校验：** logo 有默认值（`config.go` 中 `Logo: "logo.png"`），`systemName` 兜底 `Base Admin`，仅 `subtitle` 默认为空。故即使全不配置，左栏仍是「渐变 + logo 图 + Base Admin」，不会空洞。

**scrim 只在有图时应用：** 无图时左栏是纯渐变，对比度本就可控，再叠半透明遮罩只会让渐变发灰发脏。

**Alternatives considered：**
- 无图时回到居中卡片 → 拒绝，零配置用户体验零提升（见上），且两套布局 × 两套断点 = 四套样式。
- 无图时左栏留白 → 拒绝，空白的半屏比现在的居中卡片更空。

### D2：桌面/移动两张背景图，移动端缺省回退桌面图

新增 `login_bg` 与 `login_bg_mobile` 两个字段。移动端解析顺序：`login_bg_mobile` → `login_bg` → 渐变。

**Why：** 实测各视口下左栏（按 55% 宽）的宽高比为：1920×1080 → 1056×1080 ≈ **0.98:1**；1440×900 → 792×900 ≈ **0.88:1**；1280×800 → 704×800 ≈ **0.88:1**——桌面左栏**接近正方形**，而非横构图。移动端（iPhone 390×844）为 **0.46:1**（约 1:2.2 的窄长条）。同一张图 `object-fit: cover` 填充时，移动端要在宽度方向裁掉 50% 以上，主体极易被裁没。

**回退链是 D2 成立的关键而非可选便利：** 大多数使用者只会准备一张图，没有 `login_bg_mobile` → `login_bg` 的回退，移动端会直接掉回渐变，第二个字段就白加了。

**Alternatives considered：**
- 单字段 `login_bg` + `object-position` 微调 → 拒绝，把构图问题推给使用者去调一个很玄学的 CSS 值。
- 服务端按 UA 返回不同图 → 拒绝，引入 UA 嗅探与额外的图片路由，收益不抵复杂度。

### D3：背景图用 `new Image()` 预加载 + 淡入，失败回退渐变

不直接用 CSS `background-image`（无 onerror 事件），也不直接用 `<img @error>`（无法淡入）。做法：`new Image()` 预加载，`onload` 后把 URL 挂到内联 style 并触发淡入，`onerror` 保持渐变并 `console.warn`。

**Why：** 登录页是第一印象，图片「白闪 → 突然出现」很难看；同时基座不能因为一张图 404 就显示破图或白屏。

**Alternatives considered：**
- CSS `background-image` 且无降级 → 拒绝，图 404 时是纯色/白屏，且无法感知失败。
- `<img>` + `@error` → 可靠性够但没法做淡入，且要额外处理 z-index 层叠。

### D4：登录请求用 `skipGlobalError` 豁免全部全局错误呈现

登录失败要面对两个独立的全局拦截器行为：

1. **「登录已过期」弹窗**：拦截器对 HTTP 401 一律弹该弹窗。当前后端登录失败走 `utils.Fail(c, 401, ...)`，发的是 **HTTP 200 + body.code=401**，所以暂时走不到这个分支；但一旦后端改用 `FailWithStatus` / `Unauthorized` 发真 401，登录页就会弹出「登录已过期」——语义完全错误。
2. **全局 toast**：拦截器对一切非 200 响应弹 `ElMessage.error`（移动端 `showToast`）。这一条是**当前就会触发**的——于是登录失败时同一条消息既弹 toast 又显示在表单内联错误区，重复提示。

做法：登录请求带 `skipGlobalError: true`，拦截器见到该标记时跳过**一切**全局错误呈现（toast、「登录已过期」弹窗、清 token），只 reject 一个携带 message 的 Error 交给调用方内联展示。

**Why：** 「密码错误」与「会话过期」是两个语义，全局拦截器无法区分，只能由调用方声明；而「错误由调用方自行呈现」是一个完整语义，不应只豁免 401 而留下 toast 重复提示——故标记命名为 `skipGlobalError` 而非只针对重定向。提前修掉 401 这个哑弹，可避免后端任何一次鉴权响应调整就把它触发。

**Alternatives considered：**
- 只豁免 401 重定向、保留全局 toast → 拒绝，登录失败会出现「toast + 内联」双重提示，正是本决策要消除的问题。
- 依赖后端永远用 200 + code=401 → 拒绝，把前端正确性押在后端永不改动上，脆。
- 在拦截器里判断 `router.currentRoute.path === '/login'` → 拒绝，让拦截器感知路由是反向依赖。

### D5：footer 抽成组件，两端复用

新增 `frontend/src/components/AppFooter.vue` 与 `mobile/src/components/AppFooter.vue`，`Layout.vue` 与 `Login.vue` 都用它。登录页的 footer 与系统内 footer 复用同一份 `app.footer`，不新增 `login_footer` 字段。

**Why：** 「页脚」在系统里应当只有一个真相。`frontend/CLAUDE.md` 第 12 行也要求公共组件放 `components/`。

**Alternatives considered：**
- 新增 `app.login_footer` 独立配置 → 拒绝，又一个字段 = 又 4 处改动，且页脚内容在登录页与系统内高度重合（版权 / 备案 / 版本）。
- 支持 footer 渲染 HTML（为备案链接）→ **明确拒绝**，为配置文件里的一段字符串开放 HTML 注入面，收益不抵风险。备案号以纯文本渲染。

### D6：默认账号提示仅 DEV 可见

`admin / admin123` 提示（`frontend/src/views/Login.vue:30`、移动端 L32）改为 `v-if` + `import.meta.env.DEV`。

**Why：** 一个安全基座的登录页上明文印着默认凭据，是会被安全扫描直接标出来的问题。开发态需要它，生产态必须消失。

**Alternatives considered：**
- 完全删除 → 拒绝，开发/联调时确实需要，删了降低开发体验。
- 做成配置项 → 拒绝，为一个开发辅助信息增加一个配置字段不划算。

### D7：移动端采用「上部品牌区 + 下方表单」，而非表单浮于全屏背景

移动端布局为：页面上部是品牌区（背景图 + scrim + logo + 系统名 + subtitle），下方是表单区（纯色背景 + 表单 + footer）。**表单不浮在背景图之上。**

```
(b) 采用：上部品牌区 + 下方表单      (a) 否决：全屏背景 + 浮起卡片
┌──────────────┐                  ┌──────────────┐
│▓▓▓▓▓▓▓▓▓▓▓▓▓│                  │▓▓▓▓▓▓▓▓▓▓▓▓▓│
│▓ 背景图 + ▓  │                  │▓ ┌──────┐ ▓  │
│▓ 品牌块   ▓  │                  │▓ │ LOGO │ ▓  │
│▓▓▓▓▓▓▓▓▓▓▓▓▓│                  │▓ │ 用户名│ ▓  │
│              │                  │▓ │ 密码  │ ▓  │
│   用户名     │                  │▓ │[登录] │ ▓  │
│   密码       │                  │▓ └──────┘ ▓  │
│  [ 登 录 ]   │                  │▓▓▓▓▓▓▓▓▓▓▓▓▓│
│              │                  │  footer     │
│   footer     │                  └──────────────┘
└──────────────┘
```

**Why：** (a) 存在一个此消彼长的内在矛盾——卡片越不透明，表单越好读但背景图越看不见；卡片越透，图好看但表单难读。取中间值的结果通常是「图看得见但只剩边缘一圈」，使用者花力气配的图实际收益很低。(b) 没有这个矛盾：背景图在品牌区完整可见，表单区保持干净可读。移动端屏幕小，登录是核心任务，为装饰性背景牺牲可读性不划算。

**Alternatives considered：**
- 全屏背景 + 浮起卡片（a）→ 拒绝，理由如上；且沉浸感带来的收益不足以抵消可读性风险与配图收益打折。
- 移动端不分区域、仅把背景图作为页面底色 → 拒绝，等同于(a)的弱化版，同样损失配图可见性。

## Risks / Trade-offs

- [分栏布局在断点附近可能出现构图挤压] → 设定明确断点（900px），左栏在窄屏直接隐藏（`display: none`）而非压扁；在 1024 / 1280 / 1440 / 375 四档验证。
- [背景图体积失控拖慢首屏] → 文档层建议（非强制）：单张 ≤ 300KB、优先 WebP；加载期间显示渐变，表单可用性不受影响。
- [品牌块文字压在任意背景图上都可能对比度不足] → scrim 用品牌色半透明渐变（而非纯黑），并在品牌块文字上加轻微 `text-shadow` 兜底。
- [`login_bg` 与 `login_bg_mobile` 共 8 处改动易漏] → 由 `brand-config-guard` 的护栏测试强制，漏一处 `make test` 即红。**本 change 依赖 brand-config-guard 先落地。**

## Open Questions

- 是否需要引入一层 CSS 变量主题 token（`--brand-primary` 等）？当前品牌色散落在 `Layout.vue`、`Login.vue` 与各页面中，本次改动会新增更多硬编码色值。**倾向：本次只为登录页引入局部 token，全局 token 化另立 change。**
- 是否需要验证码？后端 `services.Login` 无验证码能力，但有登录日志表（`RecordLoginLog`），做「连续失败 N 次锁定」是有基础的。本次不做，建议单独立项。
- 移动端除登录页外，Home / Mine 是否也需要 footer？本次只做登录页（用户明确要求），系统内页待定。
